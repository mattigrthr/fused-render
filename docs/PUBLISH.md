# Publishing an app to the author's own hosting

fused-render hosts nothing (SPEC §1). Publishing does not change that, and this
document is mostly about how the design keeps that true while still ending with
a URL somebody can open on a phone.

The relationship is the one `mounts` already has with rclone: fused-render
drives a tool the author installed, signed into their own account, on their own
machine. It holds no account, mints no URL, sees no token, and pays for nothing.
What it contributes is everything between "here is a folder of HTML and Python"
and "here is a static site that runs that Python in a browser".

```
Publish tab  ──►  /api/publish/*  ──►  publish/runs.py
                                          │
                     export_page ─────────┤   bundle v2 (docs/EXPORT.md)
                     publish/site.py ─────┤   bundle → self-contained site
                     an adapter ──────────┘   site → the provider
```

## The two axes

Every app needs one cell from each of two independent axes, and every target
covers a region of the resulting grid.

| runtime | state |
| --- | --- |
| `runtime:js` — HTML, CSS and JavaScript only | `state:none` |
| `runtime:pyodide` — Python in the browser | `state:client-local` — each reader's own browser |
| `runtime:cpython` — Python on a real process | `state:server-backed` — one place, per reader |
| | `state:shared` — one document everyone edits |

A target is offered iff its capability set contains both of the app's cells.
That is the entire offer rule (`publish/registry.py`), and it is three lines of
set membership on purpose: an app that cannot go somewhere should be refused by
the same fact that describes the target, not by prose written separately from
the check.

**A disabled target means its adapter is not written yet, never that the
provider is incapable.** Cloudflare can run a server; fused-render has no
adapter that asks it to. The Publish page says so in those words, because
"unavailable" with no reason is how a product teaches people it is broken.

## What decides an app's two cells

`publish/eligibility.py` runs the real exporter first, so the set of files and
the list of blocking problems are identical to what a publish would hit
(`ExportPlan.errors` — `fused.writeFile`, `fused.stat`, a non-literal
`runPython` path). Then it classifies.

- **Runtime.** No Python at all is `runtime:js`. Python whose imports all exist
  in the pinned Pyodide distribution is `runtime:pyodide`. An import Pyodide
  does not have makes it `runtime:cpython`, which no adapter covers yet — and
  the report names the import, because "needs CPython" without the reason is
  unactionable. The authority is `pyodide_imports.json`, a checked-in
  projection of the distribution's own `pyodide-lock.json`, regenerated by
  `scripts/refresh_pyodide_imports.py`; a hand-written list of "packages
  Pyodide has" is wrong within a release, and was, twice, while this was built.
- **State.** Python that writes to the filesystem — `open(..., "w")`,
  `os.replace`, `pathlib.Path.write_text`, `shutil.copy` — is
  `state:client-local`. Nothing else is inferred: an app that only reads is
  `state:none`.

Some things are **notes**, not blockers, and they are the ones an author most
needs before publishing rather than after: the app's Python source becomes part
of the page and anyone can read it; a `fused.rawUrl()` on a computed path
cannot be resolved by the exporter and the files it fetches must be declared;
client-local state is each reader's alone and does not follow them to another
device.

## What a publish actually builds

`publish/site.py` turns a bundle into a directory that needs nothing but a
static file server.

```
site/
  index.html          the app's entry page, with a few tags injected
  <the author's own folder, verbatim>
  _fused/
    runtime.js        window.fused, for a page with no fused-render behind it
    boot.py           the in-browser executor
    _binding.py       copied verbatim from the engine
    site.json         what to load, and what the app shipped
    icon.svg          the author's, or a generated lettermark
    manifest.webmanifest
    pyodide/          the interpreter and every wheel in the closure
  fused-sw.js         offline cache
  _headers
```

Four things about it are load-bearing rather than incidental:

**The Python harness lives outside the app tree.** `boot.py` and `_binding.py`
are written to `/fused-runtime` in the browser filesystem, not to `/app`, and
`sys.path` gets `/fused-runtime` before `/app`. Otherwise the harness is
indistinguishable from the reader's own files and gets captured into their
saved state.

**`_binding.py` is copied, not reimplemented.** Param coercion in a published
app is byte-identical to param coercion locally because it is literally the
same source file, the same way the engine reads and exec's it (D167). A second
implementation in JavaScript would drift the first time a signature had a
default this one did not handle.

**Every wheel sits beside `pyodide-lock.json`.** `loadPackage` is called with
package NAMES, so Pyodide resolves each file against its own directory and
walks the dependency graph itself. Loading by wheel URL instead looks like it
works and then reaches for the network the moment a package has a dependency.

**The service worker is at the site root.** A worker under `_fused/` gets scope
`/_fused/` and cannot control the page; widening it needs a response header no
static host will let a subdirectory set.

## How state survives a re-publish

This is the part the whole design bends around.

Under Pyodide the filesystem is memory: it dies with the tab. An app like the
Chinese vocabulary cards persists with plain `open()` and `os.replace` — which
is correct, portable Python, and exactly what the local engine wants. Nothing
about it should have to change to be published.

So the runtime **seeds then overlays**. On every boot it writes the published
files into the browser filesystem and records each one's hash. When a
`runPython` call finishes, it walks the tree, finds what differs from what was
shipped, and stores only the differences in `localStorage` — plus a `null`
tombstone for a shipped file the reader's Python deleted. The next boot seeds
the fresh published files and lays the overlay back on top.

The consequence is the one issue #2 asks for: the author re-publishes a new
deck of cards, and the reader gets the new deck **with their progress on it**,
because the progress was never a copy of the shipped file — it was the
difference from it.

Two guards make that hold:

- The overlay is keyed by app name and, more importantly, is scoped to the
  **origin**. Which is why a re-publish must land on the same project.
- So the project is recorded in the app's own `.fused/data/publish.json`
  (SPEC §47: it cannot be rebuilt, and losing it strands every reader's
  progress behind an address nobody will visit again). The adapter refuses to
  deploy when the recorded project is gone rather than silently minting a new
  one, and the run refuses to rename a project for an app that is already live.
  Both refusals name the consequence.

`persistOverlay` throws when `localStorage` is full, before the `runPython`
promise resolves, so a save that did not happen is never reported as one that
did.

## Authentication

`wrangler login`, run by the author, approved in the author's browser. The
token lands in the provider CLI's config, which this app does not read.

There is deliberately no field to paste an API token into. It is a worse
experience, a worse security posture, and it would make fused-render the
custodian of a long-lived credential for an account it has no other
relationship with.

`auth()` is read-only and must never open a browser: it is called to draw a
row, and a page that opens an OAuth window because you looked at it is a bug.
`login()` is the only thing that can, and it is behind `X-Fused` for the same
reason every mutating endpoint is.

## The API

Six routes, `fused_render/server/routers/publish.py`.

| route | |
| --- | --- |
| `GET /api/publish/plan?path=` | the eligibility report, the targets, and what the app is already published to. No provider CLI is run. |
| `GET /api/publish/auth?target=` | one provider's sign-in state. Read-only. |
| `POST /api/publish/login` | the provider's browser approval. `X-Fused`. |
| `POST /api/publish/deploy` | starts a run; returns immediately. `X-Fused`. |
| `GET /api/publish/run?path=&target=` | poll one. `null` is not an error. |
| `POST /api/publish/forget` | stop treating a provider project as this app's. Deletes nothing at the provider. `X-Fused`. |

A publish is a background **run** rather than a long request: the first one
fetches a Python runtime and uploads over ten megabytes, and a request held
open across that is a request that times out in the middle of something
irreversible. Runs live in process memory, keyed by app and target, one at a
time per pair — two concurrent deploys race on the same project and the loser
overwrites the winner with older bytes.

## Adding a provider

1. Write a class with `id`, `label`, `blurb`, `capabilities`, `auth()`,
   `login()` and `publish(site_dir, *, name, record)` — the Protocol in
   `publish/adapter.py`. There is no base class to inherit.
2. Add one line to `registry._adapters()`.

Everything else — the eligibility scan, the site build, the run store, the
Publish page, the disabled rows with their reasons — already works for it. A
`PublishError` you raise is shown to the author verbatim, so write the message
for them.

## Cloudflare Pages, specifically

Covers `runtime:js`, `runtime:pyodide`, `state:none`, `state:client-local`.

The CLI is found at `FUSED_RENDER_WRANGLER`, then `wrangler` on `PATH`, then
`npx --yes wrangler@4`. Every invocation runs with `CI=1`,
`WRANGLER_SEND_METRICS=false` and stdin closed, so nothing can block on a
prompt fused-render cannot answer. Output is parsed by scanning for the first
balanced JSON value, because wrangler prints a banner above its `--json`.

The canonical URL is `https://<project>.pages.dev` — never the
`<hash>.<project>.pages.dev` alias a deployment also mints, which would pin
readers to a snapshot and split their saved progress across origins.

## Verifying a publish

Genuinely on a phone, on cellular, not on the author's network:

- it loads and is usable at phone width
- the Python runs
- progress survives a full browser restart
- progress survives a re-publish
- Add to Home Screen works and the icon is the app's

The last one is why the manifest and `apple-touch-icon` are not decoration: iOS
Safari deletes script-writable storage after seven days without interaction,
and a home-screen app is exempt. For an app whose whole value is a month of
accumulated review history, the manifest is what makes the storage durable.
